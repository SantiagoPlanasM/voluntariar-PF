# AI_RULES.md — Reglas para trabajar sobre VoluntariAR

> Este archivo es la guía operativa para cualquier IA (o desarrollador) que vaya a modificar este código. Léelo junto con `PROJECT_CONTEXT.md` antes de tocar cualquier archivo. Si una instrucción del usuario entra en conflicto con estas reglas, señalarlo explícitamente antes de proceder.

## Reglas base solicitadas

1. **Nunca modificar código sin entender el flujo completo.** Antes de tocar un endpoint, leer su ruta completa en `API_CONTEXT.md`, la tabla de base de datos involucrada en `DATABASE_CONTEXT.md`, y el/los componente(s) de frontend que lo consumen en `FRONTEND_CONTEXT.md`. Este proyecto tiene lógica repartida (validaciones duplicadas backend/frontend, mapeo español↔inglés) que no es visible mirando un solo archivo.
2. **No romper compatibilidad de la API.** El frontend depende de nombres de campo exactos definidos en las funciones `fmt()`/`fmtNgo()` (`BACKEND_CONTEXT.md §6, §8`). Cambiar un nombre de campo en la respuesta de un endpoint sin actualizar el `interface` correspondiente en `frontend/src/lib/api.ts` rompe la UI en silencio (TypeScript no lo detecta porque no hay contrato compartido).
3. **Evitar duplicación.** Antes de escribir una validación o helper nuevo, revisar si ya existe una versión equivalente en el otro lado de la pila (backend `routes/*.js` ↔ frontend `AuthModal.tsx`/`ProjectDetails.tsx`/`CreateVoluntariado.tsx`). Este proyecto ya tiene duplicación real (regex de auth, blacklist de palabras) — no agregar más sin una razón explícita, e idealmente proponer extraerla a un módulo compartido.
4. **Reutilizar helpers.** Usar `db.query/run/get/all` del adaptador (`src/db/index.js`), no instanciar conexiones nuevas. En frontend, usar `lib/api.ts` para llamadas HTTP — **no repetir el patrón de `fetch()` directo** que todavía existe (indebidamente) en `NGOEmpleados.tsx`; si se toca ese archivo, es buen momento para migrarlo a `api.ts` en vez de perpetuar el patrón (`NGOKPIs.tsx` tenía el mismo problema y ya se corrigió — sirve de referencia de cómo migrar). En backend, si un router nuevo necesita formatear un `Project`, **importar `fmt` desde `routes/projects.js`** (está exportado justo para esto) — no copiarlo. Ya pasó dos veces que una copia se desincronizó (`follows.js`, `ngos.js`), ver `PROJECT_ANALYSIS.md §29`.
5. **Preferir refactorización antes que parches**, pero solo cuando el usuario lo pida o el cambio lo amerite genuinamente — no refactorizar oportunistamente código no relacionado con la tarea pedida. Documentar cualquier refactor grande antes de ejecutarlo.
6. **Mantener tipado consistente.** Todo campo nuevo expuesto por el backend debe reflejarse en el `interface` TypeScript correspondiente en `api.ts`, con el tipo correcto (`string`, `number`, `boolean`, `T[]`, `T | null`). No usar `any`.
7. **Mantener una única representación de cada modelo.** No crear un segundo lugar para definir "qué es un Project" o "qué es un NGO" — la fuente de verdad de forma es `migrate.js` (DB), el mapeo es `fmt()`/`fmtNgo()` (backend), y el contrato de consumo es el `interface` en `api.ts` (frontend). Cualquier cambio de forma del modelo debe tocar los tres lugares de forma coherente.
8. **No usar `SELECT *` en endpoints públicos.** Los endpoints sin autenticación (`GET /api/projects`, `GET /api/ngos`, `GET /api/ngos/:id`, catálogos) no deben exponer columnas sensibles (p. ej. si en el futuro se agregan columnas de facturación, tokens internos, etc. a `ngos`/`users`). Seleccionar columnas explícitamente. **Cómo se cumple hoy (`PROJECT_ANALYSIS.md §86`):** `fmt`/`fmtNgo`/`fmtEmpresa` son listas blancas (nunca `...fila`), los catálogos y las subconsultas (comentarios, calificaciones, KPIs) nombran sus columnas, y `test/integration/public-columns.test.js` le agrega una columna "secreta" a cada tabla y verifica que ningún endpoint público la devuelva. Un endpoint público nuevo se suma a ese test.
9. **Documentar cualquier decisión arquitectónica** nueva (por ejemplo, si se decide implementar `donaciones` o `reuniones`, actualizar `DATABASE_CONTEXT.md` y `API_CONTEXT.md` en el mismo cambio, no dejarlo para después).
10. **Mantener consistencia entre frontend y backend.** Antes de dar por cerrada una tarea que toque un endpoint, verificar manualmente (grep, no solo lectura) que el nombre del campo en el `body` que envía el frontend coincide exactamente con el nombre que el `req.body` del backend destructura. Este proyecto ya tuvo un bug exactamente de este tipo (`message` vs `mensaje` en inscripciones, ya corregido) — no repetirlo. Este mismo principio se aplica más allá de nombres de campo: verificar también con datos reales (no solo lectura de código) cuando dos endpoints deberían devolver la misma forma de un mismo recurso — ya pasó que dos endpoints de proyectos devolvían formas distintas por tener formateadores copiados en vez de compartidos (`PROJECT_ANALYSIS.md §29`).

## Reglas adicionales específicas de este proyecto

11. **Respetar la convención español (DB) / inglés (API-frontend).** No introducir nombres de columna en inglés en `migrate.js`, ni nombres de campo en español en `api.ts`. Si hay dudas sobre a qué lado pertenece un nombre nuevo, seguir el patrón de la tabla más parecida ya existente.
12. **Cualquier cambio de esquema (`migrate.js`) debe considerarse aditivo.** Para tablas nuevas, `CREATE TABLE IF NOT EXISTS` alcanza. Para agregar una columna a una tabla existente, usar el helper `addColumnIfNotExists(tabla, columna, definición)` (agregado 2026-09, ver `PROJECT_ANALYSIS.md §29`) — chequea si la columna ya existe antes de correr el `ALTER TABLE`, así `migrate.js` se puede correr las veces que sea sin romper. No escribir un `ALTER TABLE` suelto sin ese chequeo de idempotencia. Dejar constancia en el propio script de qué migración es y cuándo se agregó.
13. **Toda query nueva debe funcionar en ambos motores (SQLite y Postgres)**, o documentar explícitamente por qué se bifurca (como ya ocurre en `GET /api/projects`, ver `BACKEND_CONTEXT.md §2`). Antes de usar una función específica de Postgres (`json_agg`, `ILIKE`, `RETURNING`, `jsonb_build_object`), confirmar que `translatePg()` la traduce o escribir la rama SQLite a mano. **Los agregados (`SUM`/`COUNT`/`AVG`) llegan como string en Postgres** (bigint/numeric; el adaptador no configura parsers de `pg`) y como número en SQLite: normalizar siempre con `Number()` en el endpoint. Los tests SQLite no lo detectan (pasan igual) — ver `PROJECT_ANALYSIS.md §33`. **Los timestamps son string en SQLite y `Date` en Postgres:** jamás usar métodos de string (`.replace`, `.localeCompare`, `.includes`) sobre columnas de fecha; todo cálculo pasa por `toMillis()` de `src/lib/time.js` (`§35`). **Las columnas BOOLEAN se comparan con `true`/`false`, nunca con `1`/`0`:** en Postgres `boolean = integer` es un error de tipos (500), y SQLite toma `true` como 1 (`§51`). **`ON CONFLICT [(cols)] DO NOTHING` funciona tal cual en ambos motores**: `translatePg` ya no lo reescribe (antes lo convertía en `OR IGNORE` en el mismo lugar, SQL inválido; `§43`).
14. **No asumir que una tabla del esquema tiene API.** `donaciones` y `reuniones` existen en la base pero no tienen endpoints (`API_CONTEXT.md`, sección "Endpoints ausentes"). Si una tarea las menciona, tratarlas como funcionalidad a construir desde cero, no a "arreglar". (`voluntario_habilidades`, `empresa_voluntariados` (Patrocinio) y `ngo_follows`/`project_follows`/`volunteer_follows` (Follows) ya tienen API completa — ver las secciones correspondientes en `API_CONTEXT.md`.)
15. **No agregar guardas de rol solo en el frontend sin el respaldo del backend, ni viceversa.** La autorización real vive en el backend (`requireRole`, verificación de `ngo_id`); cualquier guarda de UI es solo cosmética/UX y debe tratarse como tal, nunca como control de acceso real. **Todo endpoint con control de dueño (`AND ngo_id = $n`, `AND user_id = $n`) suma su caso a `test/integration/ownership.test.js`**: el intento ajeno es rechazado, la base no cambia y la dueña puede con los mismos ids (`PROJECT_ANALYSIS.md §55`).
16. **Antes de "corregir" un bug documentado en `PROJECT_ANALYSIS.md`, confirmar con el usuario si quiere que se corrija en esta tarea.** Un bug documentado como pendiente puede tener efectos secundarios (p. ej. datos ya guardados de forma inconsistente) que conviene discutir antes de tocar — aunque parezca trivial de arreglar.
17. **JWT_SECRET:** nunca hardcodear secretos nuevos. Si se toca `middleware/auth.js`, señalar (no corregir sin permiso) que el fallback `'voluntariar_dev_secret'` es inseguro para producción real y debería exigir la variable de entorno en vez de tener default.
18. **No introducir ORMs, gestores de estado globales (Redux/Zustand) ni librerías de fetching (React Query) sin que el usuario lo pida explícitamente** — el proyecto es intencionalmente minimalista en dependencias; agregar una librería grande es una decisión arquitectónica que merece discutirse, no asumirse.
19. **Mantener los mensajes de error orientados al usuario final en español**, consistentes con el resto de la API (`{ error: "..." }` en español coloquial, sin jerga técnica ni stack traces).
20. **Cuando una tarea implique tocar `enrollments.js`, `projects.js` (rutas de cupos), verificar siempre la invariante `cupos_ocupados <= cupos`** manualmente en el código, ya que no está protegida por un `CHECK` de base de datos (`DATABASE_CONTEXT.md §10.3`). Hoy la imponen el alta y la aprobación de inscripciones (`UPDATE` condicional `WHERE cupos_ocupados < cupos`, `PROJECT_ANALYSIS.md §39`); `PUT /api/projects/:id` también (`UPDATE ... WHERE cupos_ocupados <= $9`, `§40`).
21. **Todo cambio que deba dejar varias filas/tablas consistentes entre sí (estado + contador, pagos + `recaudado`) va dentro de `db.transaction()`**, usando `tx.*` y nunca `db.*` adentro (el adaptador lo rechaza con un error). Postgres corre `READ COMMITTED` con transacciones en paralelo: para evitar la doble aplicación usar `UPDATE` atómico (`SET n = n + 1`) o compare-and-swap (`WHERE status = $viejo`, mirar `changes`). Emails, notificaciones y llamadas externas van **después** del COMMIT. Un `INSERT` que puede chocar con un `UNIQUE` cuando dos pedidos pasan a la vez el chequeo previo ("¿ya existe?") se protege con `isUniqueViolation(err)` de `src/lib/dbErrors.js` → **409**, nunca 500 (los dos motores; `PROJECT_ANALYSIS.md §85`). Ver `BACKEND_CONTEXT.md §2`.
22. **Todo cambio de backend que toque queries, tipos de datos, concurrencia o el adaptador se verifica también con `npm run test:pg`**, no solo `npm test`: SQLite no reproduce carreras entre conexiones ni diferencias de tipos (`Date`, agregados como string). Ver `PROJECT_ANALYSIS.md §33` y `§34`.
23. **Al crear una fila y devolverla, generá el id en el código (`crypto.randomUUID()`), insertalo, y releé POR ID.** Nunca "la última fila por `created_at`" (`ORDER BY created_at DESC LIMIT 1` después de un `INSERT`): en SQLite `created_at` tiene resolución de 1 s y dos altas en el mismo segundo empatan, devolviendo la más vieja. Eso ya rompió proyectos (y sus categorías/roles/requisitos), empleados, comentarios, KPIs y los mensajes del chat, incluido lo que se empuja por WebSocket (`PROJECT_ANALYSIS.md §40`). En Postgres casi no se ve (microsegundos), por eso `npm run test:pg` por sí solo no lo detecta: los tests de altas deben correr también en SQLite.
24. **Toda subida de archivos de un usuario sigue este orden** (`PROJECT_ANALYSIS.md §43`): (a) sesión y rol **antes** de leer el cuerpo; (b) validar TODO —campos, permisos, límites y la **cabecera real** del archivo, nunca el `mimetype` que declara el cliente— **antes** de subir nada, para no gastar cuota del proveedor en pedidos inválidos; (c) las llamadas externas (Cloudinary) van **fuera** de `db.transaction()`, y la fila y sus archivos se guardan juntos en una sola transacción **después**; (d) si algo falla, **borrar lo ya subido** (que no queden huérfanos); (e) no exponer el id interno del proveedor (`provider_id`) ni mandar ni loguear el secreto; (f) `storage.*` se llama accediendo a la propiedad (no desestructurado) para poder reemplazarlo en los tests. Los tests nunca suben nada de verdad.
