1. Resumen y nivel declarado

VoluntariAR es una red social de voluntariado que conecta voluntarios, ONG y empresas. Backend en Node 22 + Express con SQL a mano (SQLite en desarrollo y pruebas, Postgres en producción); frontend en React 18 + Vite; desplegado en Render (plan gratuito). La integración externa evaluada es Mercado Pago (donaciones con Checkout Pro, en modo prueba). Desde el 18/10 funciona como marketplace: cada ONG cobra en su propia cuenta de vendedor y la plataforma no cobra comisión. También usa Cloudinary (archivos) y Resend (emails).

Se declaró el nivel 3 (prototipo avanzado), porque el producto estaba funcionalmente terminado y desplegado. El trabajo agregó lo que faltaba para que la calidad se apoye en datos: pipeline de CI/CD con quality gate, SonarCloud como herramienta nueva, deploy automático con smoke y E2E contra Mercado Pago, pruebas de stress y esfuerzo sostenido, plan de pruebas versionado y registro de defectos en GitHub Issues con trazabilidad.

En números: 930 tests de backend en SQLite y 932 en Postgres (UTC y zona horaria de Córdoba), 939 de frontend, todos en verde (CI #36). Cobertura del backend 93,22 % de líneas; del frontend, 90,78 % de líneas y más del 80 % en sentencias, ramas y funciones. SonarCloud: issues abiertas 157 → 0, bugs 39 → 0, vulnerabilidades 18 → 0 abiertas; aceptadas con justificación 14 → 4; cobertura del código nuevo 90,8 %. 3 ejecuciones fallidas reales del CI, todas corregidas en commits posteriores. 29 defectos registrados con pasos, esperado y obtenido, todos corregidos con su commit y su prueba de regresión. El frontend se rediseñó entero durante el TP y la suite encontró sus regresiones antes del commit (sección 7). 69 commits durante el TP.

  • Dependencia del contexto: para la plata se prueba concurrencia y montos límite; para las pantallas, roles accesibles.
  • Falacia de la ausencia de errores: por eso existe la validación por rol, además de la verificación.

4.3 Procesos de QA/QC y gestión

QA (proactivo, sobre el proceso):

  • las 24 reglas de AI_RULES.md;
  • tests primero;
  • revisiones de código;
  • un commit por tarea;
  • el quality gate;
  • la sección "no verificado" de cada cambio.

QC (reactivo, sobre el producto):

  • las suites;
  • el smoke y el E2E;
  • la carga;
  • la verificación manual en producción.

Ciclo de vida del defecto (PLAN_PRUEBAS.md §10):

  1. Reportado: el hallazgo en una revisión, un run rojo, SonarCloud o producción.
  2. Triage: labels de severidad, origen y área, o la aceptación justificada de TRIAGE_SONAR.md.
  3. Asignado: no se usó el campo de GitHub; somos dos y nos repartimos de palabra.
  4. Verificado: la prueba de regresión pasa de rojo a verde en el CI.
  5. Cerrado: el Issue se cierra con el commit.

Honestidad: los 21 primeros Issues se cargaron después de los arreglos; cada uno se abrió y se cerró en segundos. El ciclo real quedó en REVISION.md y en los commits. Los 8 de la sesión exploratoria sí siguieron el ciclo completo: se reportaron como Issues abiertos (#23–#30), se clasificaron (severidad, área, encontrado:exploratoria), se corrigieron con un test que primero falló y se cerraron cuando ese test pasó en el CI (el paso "verificado").

Planificación y estimación de esfuerzo. El plan (PLAN_CALIDAD_TP.md §3) estimó cada tarea por juicio de expertos, con tamaños S, M y L, en 9 días de calendario (17/10 a 25/10). No había datos históricos de tareas parecidas, porque era el primer pipeline del proyecto. Lo real: las tareas T0–T13 se cerraron entre el primer y el último commit del 17/10 (12:04 a 22:45, git log), y el marketplace se agregó el 18/10. La estimación sobrestimó mucho, sobre todo porque no contempló la asistencia de IA. Ese registro con hora de cada commit es el dato histórico para estimar la próxima vez; la hora de un commit no es esfuerzo medido, pero acota la duración real.

Matriz de riesgos (probabilidad × impacto). Hay 10 riesgos en PLAN_PRUEBAS.md §6, y la matriz definió dónde poner más pruebas:

  • "una consulta falla solo en Postgres" (P×I = 6) → toda la suite corre dos veces, una en cada motor;
  • "doble acreditación" (impacto 3) → tests de avisos repetidos y simultáneos;
  • "la carga tira el servicio" (6) → solo pedidos GET y carga acotada;
  • "Render dormido en la demo" (9) no se puede probar → plan de contingencia.

4.6 Automatización y ecosistema de herramientas

Pirámide. La base son las unitarias y la integración de API del backend (929 tests), que corren en segundos y sin red. En el medio, los 939 tests de componentes y funciones del frontend. La punta es el E2E contra Mercado Pago y el smoke: un recorrido por deploy, lento y con un servicio real. Lectura honesta: la punta sí es angosta, pero la base no es más ancha que el medio (desde el rediseño, el medio es incluso un poco más ancho), así que la forma se parece más a un rectángulo con punta que a una pirámide. La base de integración de API es donde aparecieron casi todos los defectos. No hay E2E de interfaz (Selenium o Cypress): la interfaz se prueba con Testing Library sobre jsdom y con el recorrido manual. Es una decisión de costo y queda como brecha. CI/CD: ci.yml en cada push → deploy.yml solo si el CI está en verde.

function detectImageType(buf) {
  if (!Buffer.isBuffer(buf)) return null;
  if (buf.length >= 3 && buf[0] === 0xff && buf[1] === 0xd8 && buf[2] === 0xff) return 'jpeg';
  if (buf.length >= 8 && buf.subarray(0, 8).equals(Buffer.from([0x89, 0x50, 0x4e, 0x47, 0x0d, 0x0a, 0x1a, 0x0a]))) return 'png';
  if (buf.length >= 12 && buf.toString('latin1', 0, 4) === 'RIFF' && buf.toString('latin1', 8, 12) === 'WEBP') return 'webp';
  return null;
}
function detectPdf(buf) {
  return Buffer.isBuffer(buf) && buf.length >= 5 && buf.toString('latin1', 0, 5) === '%PDF-';
}

function checkText(value, { label, max, min = 0, required = false, nullable = !required }) {
  if (value === undefined) return required ? `${label} es obligatorio` : null;
  if (value === null) return nullable ? null : `${label} es obligatorio`;
  if (typeof value !== 'string') return `${label} tiene que ser un texto`;
  const len = value.trim().length;
  if (required || !nullable || min > 0) {
    if (len === 0) return `${label} no puede estar vacío`;
    if (len < min) return `${label} tiene que tener al menos ${min} caracteres`;
  }
  if (value.length > max) return `${label} puede tener hasta ${max} caracteres`;
  return null;
}

7.3 Un test intermitente que era un defecto (D21)

Ya con el commit, el CI #34 falló en ProjectDetailsRating.test.tsx. En local pasaba siempre, incluso 6 corridas seguidas con cobertura. La causa: la precarga de la reseña propia corría en un useEffect, así que había un render con la sección "Reseñas" visible y el formulario en 5 estrellas y vacío.

  • Por qué apareció con el rediseño: antes, el test hacía clic en una pestaña, y ese clic le daba tiempo al efecto. Sin pestañas, el test esperaba solo el título y a veces lo encontraba en ese render intermedio.
  • No era un test para silenciar: en el navegador era un parpadeo real de un frame.
  • Cómo se comprobó: un MutationObserver miró el DOM en cada cambio. Con el código viejo el estado intermedio aparece; con el arreglo, no.
  • El arreglo: se corrigió el código (useLayoutEffect), no el test.

El otro test inestable del proyecto (el de ReDoS, sección 8) es un problema del umbral de tiempo; este era un defecto.

8. Análisis crítico

  • Las herramientas encontraron lo que las pruebas no. Con 782 tests en verde, SonarCloud encontró una denegación de servicio real: un email de 80.000 caracteres bloqueaba toda la API 3,4 s por pedido (reproducido y corregido con un tope antes del regex). También encontró una inyección en los logs desde el webhook de Mercado Pago. Y una de sus sugerencias (localeCompare para ordenar) habría roto la firma de Cloudinary: el análisis estático hay que leerlo con criterio, no obedecerlo.
  • Los defectos escapados vienen de lo que los dobles no ven. Los 4 defectos encontrados en producción salieron de flujos con un servicio real o de lo que ve otro rol (el panel de la ONG después de una donación real). De ahí el E2E contra Mercado Pago en cada deploy. La tasa (13,8 %, 4 de 29) es sobre una selección de defectos: con todos los hallazgos de las revisiones sería menor.
  • El frontend era la deuda. En el CI #15 la cobertura de ramas (74 %) y de funciones (68 %) del frontend no llegaba al 80 %. Con un test de contrato del cliente HTTP, tests de componentes y el borrado de código muerto pasó a 81,18 % y 82,11 % (CI #19). Su densidad de pruebas subió de 60,6 a 75,9 tests/KLOC y, con el rediseño, a 88,8 (CI #36), que sigue siendo bastante menos que la del backend (154,6). Los componentes más complejos hoy, el detalle del proyecto (cognitiva 112) y la creación de voluntariados (91), son los menos probados en sus caminos de error.
  • No se encontró el punto de quiebre. Con lecturas y los datos de demo, la API no se degradó hasta 100 usuarios. Encontrarlo exige más usuarios, más datos o escrituras, que se dejaron afuera a propósito para no crear datos ni gatillar los limitadores.
  • Producción es unas 100 veces más lenta que el runner (mediana 103 ms contra 1,4 ms). Es esperable en el plan gratuito, pero no se midió qué parte es CPU, base de datos o red.
  • El proceso tuvo errores propios, y quedaron documentados: un comando del CI que no corría tests (el primer run fallido), una cobertura inflada en el pipeline, un test de tiempo inestable, un test que quedó dependiendo de la velocidad de la máquina (D21), un registro de defectos que al principio dejaba afuera 3 escapados, y el orden del proceso de la herramienta nueva (se eligió con el borrador de la matriz). Cada uno está en PROJECT_ANALYSIS.md con su corrección.
  • El marketplace volvió a mostrar lo mismo. Con todas las suites en verde, el análisis de SonarCloud sobre el código nuevo encontró 3 inyecciones en logs (S5145), que contradicen una regla que el propio proyecto se había puesto. El gate no las bloqueó porque eran de severidad menor, y se corrigieron en el commit siguiente. En el pipeline, la guarda de "faltan secretos o variables" cortó el Deploy #14 antes de desplegar: la variable del proyecto de prueba se había cargado como secret y el workflow la leía como variable. Se corrigió en 18 minutos. Además, el E2E donaba al primer proyecto de la lista, que era uno real. Ahora dona siempre a un proyecto de prueba y antes comprueba que su ONG tenga Mercado Pago vinculado.
  • Un test de tiempo es inestable en local. email-redos.test.js exige que el email malicioso se rechace en menos de 500 ms. Con la suite completa corriendo en paralelo en una PC con Windows, falló en 2 de 5 corridas (538 y 700 ms) sin ningún cambio de código. En el CI (Linux) no falló nunca. El regex ya es lineal (§231), así que es el umbral, no un ReDoS. Queda registrado como riesgo RP10 (test inestable), sin tocar todavía.
  • Diseñar la transición de estados encontró un punto ciego en las pruebas. Liberar un cupo tiene piso en 0. Si el proyecto empezaba sin cupos ocupados, "cancelar una pendiente resta un cupo" daba el mismo resultado que el código correcto. Por eso el test nuevo arranca siempre con otra persona aprobada, y con eso el mutante muere.
  • La exploración encontró lo que 939 tests no. En una sesión de 12 minutos aparecieron dos textos ilegibles en modo oscuro (uno con contraste 1,10:1), respuestas del asistente que nombran pantallas que ya no existen (el contenido vive en el backend y el rediseño fue en el frontend) y dos voluntariados que Explorar esconde a una voluntaria. Ese último pasa con las 8 recomendaciones de los datos de prueba y no con las menos de 6 de los tests: los datos de prueba eran demasiado chicos (dependencia del contexto). Se abrieron como Issues antes de tocarlos y se corrigieron los ocho, cada uno con un test que primero falló. El de contraste es un test estático que cruza las dos paletas de theme.css con todos los componentes, y encontró otros 5 casos del mismo defecto (por ejemplo, el botón de borrar la cuenta, con 2,79:1 en oscuro). El de las respuestas mostró que migrate.js no actualizaba las FAQs ya cargadas, así que el arreglo del texto no habría llegado a producción. Al ampliar el test de contraste a los textos de color aparecieron 22 casos más en las pantallas que no se rehicieron. No se arreglaron todos: el test quedó como trinquete (la lista de conocidos solo puede bajar y no puede aparecer uno nuevo), una forma medible de pagar esa deuda de a poco (SESION_EXPLORATORIA.md §7).
  • Dos gates. El gate propio del TP (con los umbrales del enunciado) y el "Sonar way" de SonarCloud son distintos. El plan gratuito no permite configurar el segundo, y eso obligó a escribir el primero. En 7b05f02 se separaron de verdad: SonarCloud quedó en rojo por un bug mayor y el gate del TP pasó, porque solo bloquea los críticos (sección 7.4). Sumarle la fiabilidad del código nuevo es una mejora barata. En la comparación de mercado, Codacy ofrece gates configurables gratis para open source: quedó a 8 puntos en la matriz y es una alternativa a probar.

9. Conclusiones

El sistema se prueba automáticamente en cada despliegue (smoke y E2E contra Mercado Pago después de cada deploy), sus integraciones externas están probadas o controladas (contrato y dobles en cada push, prueba real a mano y E2E automatizado; contingencia documentada para cada dependencia), y las decisiones de calidad se apoyan en datos (el gate bloqueó de verdad, la mejora se midió en análisis sucesivos y cada número del informe se puede rastrear hasta su ejecución). El rediseño completo del frontend, al final del TP, mostró que la suite sirve como red de regresión. Encontró cinco regresiones antes del commit, el pipeline frenó el deploy con un test en rojo y el análisis estático vio lo que los tests no.

Se cumplen todas las metas del nivel 3. La última fue la cobertura del código existente del frontend: estaba parcial (solo líneas sobre el 80 %) y quedó cumplida en las cuatro métricas en el CI #19. El E2E se cumple con un límite explícito: llega hasta crear la preferencia en Mercado Pago, ya con el token de la ONG dueña del proyecto, pero sin el pago. El pago completo, con la plata acreditada en la cuenta de prueba de la ONG, se verificó a mano.

Trabajo futuro: pruebas de regresión visual o un E2E de interfaz, que el rediseño mostró necesarios; sumar al gate del TP la fiabilidad del código nuevo; medir la calidad en uso con usuarios reales (tareas y una encuesta SUS con ONG y voluntarios); más sesiones exploratorias, hechas por personas y con otros charters; bajar a 0 los 22 casos de contraste conocidos del trinquete; un E2E de interfaz para el recorrido de la donación; estabilizar el test de tiempo del ReDoS; subir la cobertura de ramas del frontend en los componentes más complejos; una prueba de carga que busque el punto de quiebre; una prueba de concepto de Codacy; conciliar las donaciones pendientes. En el marketplace falta probar en vivo la vinculación por OAuth (el botón "Vincular Mercado Pago") y la renovación del token: el código está probado con dobles, pero necesita el client_secret de la aplicación, que solo aparece al activar las credenciales productivas. Para la demo, la ONG de prueba se vinculó cargando a mano el token de su vendedor de prueba.
