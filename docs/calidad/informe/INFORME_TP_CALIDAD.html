1. Resumen y nivel declarado

VoluntariAR es una red social de voluntariado que conecta voluntarios, ONG y empresas. Backend en Node 22 + Express con SQL a mano (SQLite en desarrollo y pruebas, Postgres en producción); frontend en React 18 + Vite; desplegado en Render (plan gratuito). La integración externa evaluada es Mercado Pago (donaciones con Checkout Pro, en modo prueba). Desde el 18/10 funciona como marketplace: cada ONG cobra en su propia cuenta de vendedor y la plataforma no cobra comisión. También usa Cloudinary (archivos) y Resend (emails).

Se declaró el nivel 3 (prototipo avanzado), porque el producto estaba funcionalmente terminado y desplegado. El trabajo agregó lo que faltaba para que la calidad se apoye en datos: pipeline de CI/CD con quality gate, SonarCloud como herramienta nueva, deploy automático con smoke y E2E contra Mercado Pago, pruebas de stress y esfuerzo sostenido, plan de pruebas versionado y registro de defectos en GitHub Issues con trazabilidad.

En números: 907 tests de backend en SQLite y 909 en Postgres (UTC y zona horaria de Córdoba), 904 de frontend, todos en verde (CI #29). Cobertura del backend 93,22 % de líneas; del frontend, 90,42 % de líneas y más del 80 % en sentencias, ramas y funciones. SonarCloud: issues abiertas 157 → 0, bugs 39 → 0, vulnerabilidades 18 → 0 abiertas; aceptadas con justificación 14 → 4; cobertura del código nuevo 93,0 %. 2 ejecuciones fallidas reales del CI, ambas corregidas en commits posteriores. 18 defectos registrados con pasos, esperado, obtenido, commit y prueba de regresión. 61 commits durante el TP.

3.1 Introducción a la calidad: objetivos y contingencia

13 objetivos medibles agrupados por usuario (rendimiento, deploys verificados, seguridad, accesibilidad), equipo (cero regresiones, cobertura, regresión por defecto, tiempo de recuperación) y organización (costo $0, dependencias sin vulnerabilidades, defectos escapados, continuidad de la demo). El mismo test de regresión corrido en worktrees aparte: sobre el commit anterior al arreglo, 2/2 en rojo ("computadora" → 400, "imbécil" → 201); sobre el arreglo, 2/2 en verde.   • Los siete principios, con un ejemplo del proyecto cada uno (PLAN_PRUEBAS.md §9). El más visible: "las pruebas muestran la presencia de defectos, no su ausencia". Con la suite en verde, 4 defectos aparecieron recién en producción.
  • Mutation testing sobre todo el código nuevo, con corrida de control. Encontró huecos reales en los tests: por ejemplo, el mínimo de 8 caracteres de la contraseña no tenía prueba de borde (D14).

4. Validaciones de entrada: el código y sus pruebas

Todo dato que llega del cliente se valida en el servidor, que es el único lugar confiable. El frontend repite algunas reglas con el mismo mensaje para avisar antes de enviar, pero no reemplaza al backend. Criterios comunes: primero se verifica el tipo (un número o un array donde se espera texto daba 500; ahora da 400, REVISION B13), después los límites, y el error vuelve como 400 con un mensaje en español, sin tocar la base ni los servicios externos. Los fragmentos son el código actual (d7efe16), sin cambios; se sacaron solo comentarios.

function amountError(amount) {
  if (typeof amount !== 'number' || !Number.isInteger(amount)) return 'El monto tiene que ser un número entero de pesos';

4.2 Contraseña

backend/src/routes/auth.js:55 · Regla: mínimo 8 caracteres, como máximo 72 bytes UTF-8 (bcrypt ignora lo que pasa de 72 bytes: dos contraseñas iguales en esos bytes valdrían como la misma), al menos una mayúscula y un número.

const PASSWORD_MAX_BYTES = 72;
function validatePassword(v) {
  if (typeof v !== 'string' || v.length < 8) return 'Mínimo 8 caracteres';
  if (Buffer.byteLength(v, 'utf8') > PASSWORD_MAX_BYTES)
    return 'Máximo 72 caracteres (los acentos, la ñ y los emojis cuentan como más de uno)';
  if (!/[A-Z]/.test(v))       return 'Necesita al menos una mayúscula';
  if (!/[0-9]/.test(v))       return 'Necesita al menos un número';
  return null;
}

Pruebas: test/unit/validators.test.js ("valores límite": 7/8 caracteres, 72/73 bytes en ASCII y con ñ, entradas que no son texto) y test/integration/register-password-max.test.js. El frontend tiene la misma regla (AuthModal.tsx:32, con TextEncoder para contar bytes). La mutación encontró que el mínimo de 8 no tenía prueba de borde (D14).

4.3 Email, con tope antes del regex (ReDoS)

backend/src/routes/auth.js:37–49 · Regla: formato algo@dominio.xx y como máximo 254 caracteres (RFC 5321). El tope va antes del regex: SonarCloud marcó el regex viejo y se reprodujo una denegación de servicio real (un email de 80.000 caracteres bloqueaba toda la API 3,4 s por pedido). El regex nuevo, además, es lineal (§231).

const EMAIL_RE = /^[^\s@]+@[^\s@][^\s@.]*\.[^\s@]{2,}$/;
const EMAIL_MAX = 254;
function validateEmail(v) {
  if (typeof v !== 'string') return 'Email inválido';
  const email = v.trim();
  if (email.length > EMAIL_MAX || !EMAIL_RE.test(email)) return 'Email inválido';
  return null;
}

Prueba: test/integration/email-redos.test.js manda el email malicioso a /login y /register y, 20 ms después, un /health: los dos tienen que responder en menos de 500 ms (400 "Email inválido" y 200). Además, test/unit/regexLineales.test.js compara el regex nuevo con el viejo en todas las cadenas cortas (aceptan lo mismo) y mide el peor caso.

4.5 Archivos subidos: el tipo real, no el declarado

backend/src/lib/storage.js:76 y :166 · Regla: el Content-Type lo escribe quien sube el archivo, así que no sirve para decidir. Se leen los primeros bytes (la "firma" del formato): fotos JPEG, PNG o WebP; CV en PDF. Tope de 8.000.000 bytes por archivo (multer). Orden de la regla 24 de AI_RULES.md: sesión y rol → límite de frecuencia → validar todo → subir a Cloudinary → guardar → borrar lo subido si algo falla.

function detectImageType(buf) {
  if (!Buffer.isBuffer(buf)) return null;
  if (buf.length >= 3 && buf[0] === 0xff && buf[1] === 0xd8 && buf[2] === 0xff) return 'jpeg';
  if (buf.length >= 8 && buf.subarray(0, 8).equals(Buffer.from([0x89, 0x50, 0x4e, 0x47, 0x0d, 0x0a, 0x1a, 0x0a]))) return 'png';
  if (buf.length >= 12 && buf.toString('latin1', 0, 4) === 'RIFF' && buf.toString('latin1', 8, 12) === 'WEBP') return 'webp';
  return null;
}
function detectPdf(buf) {
  return Buffer.isBuffer(buf) && buf.length >= 5 && buf.toString('latin1', 0, 5) === '%PDF-';
}

4.7 Textos libres y números del body

backend/src/lib/inputs.js:13 y :37 · Un solo helper para los textos de perfiles, empleados y proyectos (tipo, vacío, mínimo y máximo) y un entero estricto para cupos, horas y reseñas. Antes cada ruta hacía name.trim() por su cuenta: un número reventaba con 500, "" se salteaba y no había largo máximo (REVISION B12 y B13); y parseInt aceptaba 3.7 como 3 y "1e21" como 1 (B3).

function checkText(value, { label, max, min = 0, required = false, nullable = !required }) {
  if (value === undefined) return required ? `${label} es obligatorio` : null;
  if (value === null) return nullable ? null : `${label} es obligatorio`;
  if (typeof value !== 'string') return `${label} tiene que ser un texto`;
  const len = value.trim().length;
  if (required || !nullable || min > 0) {
    if (len === 0) return `${label} no puede estar vacío`;
    if (len < min) return `${label} tiene que tener al menos ${min} caracteres`;
  }
  if (value.length > max) return `${label} puede tener hasta ${max} caracteres`;
  return null;
}

const toStrictInt = (value) => {
  if (typeof value === 'number') return Number.isInteger(value) ? value : Number.NaN;
  if (typeof value === 'string' && /^-?\d+$/.test(value)) return Number(value);
  return Number.NaN;
};

6. Análisis crítico

  • Las herramientas encontraron lo que las pruebas no. Con 782 tests en verde, SonarCloud encontró una denegación de servicio real: un email de 80.000 caracteres bloqueaba toda la API 3,4 s por pedido (reproducido y corregido con un tope antes del regex). También encontró una inyección en los logs desde el webhook de Mercado Pago. Y una de sus sugerencias (localeCompare para ordenar) habría roto la firma de Cloudinary: el análisis estático hay que leerlo con criterio, no obedecerlo.
  • Los defectos escapados vienen de lo que los dobles no ven. Los 4 defectos encontrados en producción salieron de flujos con un servicio real o de lo que ve otro rol (el panel de la ONG después de una donación real). De ahí el E2E contra Mercado Pago en cada deploy. La tasa (22,2 %) es sobre una selección de defectos: con todos los hallazgos de las revisiones sería menor.
  • El frontend era la deuda. En el CI #15 la cobertura de ramas (74 %) y de funciones (68 %) del frontend no llegaba al 80 %. Con un test de contrato del cliente HTTP, tests de componentes y el borrado de código muerto pasó a 81,18 % y 82,11 % (CI #19). Su densidad de pruebas subió de 60,6 a 75,9 tests/KLOC, que sigue siendo cerca de la mitad de la del backend. Los componentes más complejos (Explorar, el detalle del proyecto, el mapa) son los menos probados en sus caminos de error.
  • No se encontró el punto de quiebre. Con lecturas y los datos de demo, la API no se degradó hasta 100 usuarios. Encontrarlo exige más usuarios, más datos o escrituras, que se dejaron afuera a propósito para no crear datos ni gatillar los limitadores.
  • Producción es unas 100 veces más lenta que el runner (mediana 103 ms contra 1,4 ms). Es esperable en el plan gratuito, pero no se midió qué parte es CPU, base de datos o red.
  • El proceso tuvo errores propios, y quedaron documentados: un comando del CI que no corría tests (el primer run fallido), una cobertura inflada en el pipeline, un test de tiempo inestable, un registro de defectos que al principio dejaba afuera 3 escapados, y el orden del proceso de la herramienta nueva (se eligió con el borrador de la matriz). Cada uno está en PROJECT_ANALYSIS.md con su corrección.
  • El marketplace volvió a mostrar lo mismo. Con todas las suites en verde, el análisis de SonarCloud sobre el código nuevo encontró 3 inyecciones en logs (S5145), que contradicen una regla que el propio proyecto se había puesto. El gate no las bloqueó porque eran de severidad menor, y se corrigieron en el commit siguiente. En el pipeline, la guarda de "faltan secretos o variables" cortó el Deploy #14 antes de desplegar: la variable del proyecto de prueba se había cargado como secret y el workflow la leía como variable. Se corrigió en 18 minutos. Además, el E2E donaba al primer proyecto de la lista, que era uno real. Ahora dona siempre a un proyecto de prueba y antes comprueba que su ONG tenga Mercado Pago vinculado.
  • Dos gates. El gate propio del TP (con los umbrales del enunciado) y el "Sonar way" de SonarCloud son distintos. El plan gratuito no permite configurar el segundo, y eso obligó a escribir el primero. En la comparación de mercado, Codacy ofrece gates configurables gratis para open source: quedó a 8 puntos en la matriz y es una alternativa a probar.

7. Conclusiones

El sistema se prueba automáticamente en cada despliegue (smoke y E2E contra Mercado Pago después de cada deploy), sus integraciones externas están probadas o controladas (contrato y dobles en cada push, prueba real a mano y E2E automatizado; contingencia documentada para cada dependencia), y las decisiones de calidad se apoyan en datos (el gate bloqueó de verdad, la mejora se midió en análisis sucesivos y cada número del informe se puede rastrear hasta su ejecución).

Se cumplen todas las metas del nivel 3. La última fue la cobertura del código existente del frontend: estaba parcial (solo líneas sobre el 80 %) y quedó cumplida en las cuatro métricas en el CI #19. El E2E se cumple con un límite explícito: llega hasta crear la preferencia en Mercado Pago, ya con el token de la ONG dueña del proyecto, pero sin el pago. El pago completo, con la plata acreditada en la cuenta de prueba de la ONG, se verificó a mano.

Trabajo futuro: subir la cobertura de ramas del frontend en los componentes más complejos; una prueba de carga que busque el punto de quiebre; una prueba de concepto de Codacy; conciliar las donaciones pendientes. En el marketplace falta probar en vivo la vinculación por OAuth (el botón "Vincular Mercado Pago") y la renovación del token: el código está probado con dobles, pero necesita el client_secret de la aplicación, que solo aparece al activar las credenciales productivas. Para la demo, la ONG de prueba se vinculó cargando a mano el token de su vendedor de prueba.
